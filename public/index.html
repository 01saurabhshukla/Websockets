Read me first

Everything here was built to understand WebSockets, not to ship them.

I wanted to know what actually happens on a WebSocket connection — how frames travel, how a server fans one message out to many clients, and who gets to decide what's true when two people act at once. So I built three small demos, each one answering a question I had. It's deployed and live, so go ahead and play with it — just don't mistake it for a product.

Three questions, three demos
Demo 01 Protocol

Echo

What does a frame actually look like going out and coming back? The plainest possible round trip, with nothing in the way.

  • every frame logged, sent and received
  • 150 KB payload button to watch fragmentation
  • live sent / received counters
  • close codes shown verbatim
learned: framing, backpressure, close codes
Demo 02 Fan-out

Rooms

How does one message reach many sockets? Rooms are just a map of names to connection sets — the interesting part is keeping it correct as people leave.

  • join and leave arbitrary rooms
  • broadcast to every member at once
  • direct messages to a single connection
  • typing indicators with server timeouts
learned: fan-out, presence, cleanup on disconnect
Demo 03 State

Tic-Tac-Toe

Who decides what's true? The client never owns the board — it asks, the server rules, and everyone watching gets the same answer.

  • server validates every single move
  • play as X or O, or spectate live
  • state pushed to players and spectators alike
  • abandoned games handled on disconnect
learned: authoritative state, turn locking
Why it exists

Built out of curiosity — that's the whole reason

This is a portfolio project, not a product. Every feature exists because I got curious mid-way through the previous one. The echo demo made me wonder how broadcasting works; broadcasting made me wonder who arbitrates conflicting moves; that became the game.

The UI is deliberately instrument-like — logs, counters, and raw frame contents on screen at all times — because the point was to see the protocol, not to hide it behind a pretty chat window.

Being clear about scope
What it is
  • A playground for watching WebSocket behaviour in real time
  • Three self-contained demos, each answering one question
  • Readable, deliberately un-clever code
  • A heartbeat strategy — ping/pong keeps dead sockets from lingering
  • Something to open in two browser tabs and poke at
What it is not
  • No authentication, authorisation, or rate limiting
  • No database — all state dies with the server restart
  • No input validation or abuse protection
  • Fine to demo publicly; not something I'd put real users' data through

What I want to build next

Reconnection with message replay

next up

Drop the Wi-Fi mid-game and pick up where you left off — exponential backoff on the client, a short buffer of missed frames on the server.

Binary frames

next up

Send an image or an audio blob instead of text, and see how binary frames differ from the JSON envelope everything currently uses.

Redis-backed rooms

exploring

Right now rooms live in one process's memory. Pub/sub would let two server instances share the same room — the real answer to "how does this scale?"

Schema validation on every message

exploring

A single validated envelope shape, rejected at the door instead of trusted. The obvious gap in the current build, and the one I most want to close.

A latency inspector

idea

Round-trip time per frame, charted live. Mostly because I'd like to see what a slow connection actually looks like.

Optimistic UI on the game

idea

Paint the move instantly, roll it back if the server disagrees — the thing every real-time app does, and the next question my curiosity is heading toward.
